# Full Mailbox SQLite Index Design

## Context

Milestone 1 proved that Thunderbird can push selected-message data into the
local FastAPI backend. Milestone 2 EDA showed that Thunderbird runtime
`message.id` values are not durable identities: they change across Thunderbird
restart. The durable key should be normalized RFC `Message-ID` when present,
with account, folder, and runtime ids modeled as observation and location data.

The next phase creates a SQLite-backed local mailbox index across every real
account-owned Thunderbird folder before any RAG or LLM behavior is added. The
goal is to spend time finding move, delete, duplicate, restart, provider-label,
and partial-failure bugs while the system is still only a sync/indexing tool.

## Goals

- Store messages from all account-owned Thunderbird folders.
- Exclude virtual, unified, and tag/search folders from the source traversal.
- Keep folder type metadata such as Inbox, Archive, Sent, Trash, and Junk
  instead of filtering those folders out.
- Use normalized RFC `Message-ID` as the canonical identity when available.
- Preserve location and observation records so moves and duplicates are
  debuggable instead of collapsed away.
- Add backend debug endpoints that make sync state, duplicates, inactive
  locations, and folder errors visible.
- Build enough automated and manual tests to clean up edge cases before RAG.

## Non-Goals

- No embeddings, vector database, retrieval prompts, chat UI, or LLM calls.
- No native messaging or backend-driven Thunderbird polling.
- No permanent Thunderbird UI beyond the current browser-action flow unless
  needed for observability.
- No attempt to index virtual, unified, or tag/search folders in this phase.

## Architecture

Thunderbird remains the mail source of truth. The extension performs traversal
because only it can call Thunderbird WebExtension APIs. The backend owns durable
storage, idempotent ingestion, run summaries, and debug views.

The flow is:

1. User clicks the Thunderbird extension action.
2. Extension opens an index run with the backend.
3. Extension traverses every account returned by `messenger.accounts.list(true)`.
4. Extension recursively visits account-owned folders, skipping folders where
   `isUnified`, `isVirtual`, or `isTag` is true.
5. Extension paginates each folder with `messenger.messages.list(folder)` and
   `messenger.messages.continueList(page.id)`.
6. Extension fetches each message body/header tree with
   `messenger.messages.getFull(message.id)`.
7. Extension posts message observations in batches to the backend.
8. Extension posts folder observations and errors as it goes.
9. Extension finishes the index run.
10. Backend marks previously active locations missing from the completed run as
    inactive.

## SQLite Store

Use Python's standard `sqlite3` module. Do not add an ORM. The FastAPI app should
accept an injected store object or path so tests can use temporary database
files. Runtime storage should default to `data/thunderbird_ai.sqlite`, with an
environment override for local experiments.

### `index_runs`

Tracks one full traversal attempt.

- `id`: text primary key generated by the backend.
- `started_at`: UTC timestamp.
- `finished_at`: UTC timestamp, nullable until completion.
- `status`: `running`, `completed`, or `failed`.
- `folder_count`: total folders observed.
- `message_observation_count`: total message observations accepted.
- `error_count`: total folder or message errors.
- `summary_json`: compact JSON summary for debug endpoints.

### `canonical_messages`

Stores message-level identity and latest canonical content metadata.

- `canonical_key`: text primary key.
- `identity_kind`: `message_id` or `fallback_hash`.
- `message_id`: normalized RFC Message-ID, nullable for fallback identities.
- `subject`, `author`, `recipients_json`, `date`: latest observed headers.
- `body_text`: latest extracted plain-text body.
- `body_sha256`: hash of `body_text`.
- `headers_json`: selected normalized headers for debugging.
- `first_seen_at`: UTC timestamp.
- `last_seen_at`: UTC timestamp.

### `message_locations`

Stores the latest known state of a message in an account folder.

Unique key:

- `canonical_key`
- `account_id`
- `folder_id`

Fields:

- `folder_path`
- `folder_name`
- `folder_special_use_json`
- `is_unified`
- `is_virtual`
- `is_tag`
- `active`
- `first_seen_at`
- `last_seen_at`
- `last_runtime_message_id`
- `last_observed_run_id`

Moves should create or reactivate a destination location and eventually mark the
old source location inactive. Duplicate provider labels should appear as
multiple active locations for one canonical key.

### `message_observations`

Stores run-scoped evidence of what Thunderbird reported.

Unique key:

- `run_id`
- `runtime_message_id`

Fields:

- `canonical_key`
- `identity_kind`
- `account_id`
- `folder_id`
- `folder_path`
- `runtime_message_id`
- `message_id`
- `subject`
- `author`
- `date`
- `body_sha256`
- `observed_at`
- `error_json`

This table is the primary audit trail when a later debug endpoint reports that a
message moved, disappeared, duplicated, or changed runtime ids after restart.

### `folder_observations`

Stores folder-level traversal evidence.

Unique key:

- `run_id`
- `account_id`
- `folder_id`

Fields:

- `folder_path`
- `folder_name`
- `folder_special_use_json`
- `is_unified`
- `is_virtual`
- `is_tag`
- `included`
- `message_count_seen`
- `error_json`
- `observed_at`

Skipped virtual/unified/tag folders should be recorded with `included = false`
when they are encountered, so the traversal decision is inspectable.

## Identity Rules

Normalize RFC `Message-ID` by trimming whitespace, removing wrapping angle
brackets, and lowercasing. Store the normalized value without angle brackets.

If no Message-ID is available, create a fallback hash from stable headers and
body hash. The fallback should be explicit by setting `identity_kind` to
`fallback_hash`. Fallback identities are acceptable but should be counted in run
summaries because they are less trustworthy than RFC Message-ID.

Runtime Thunderbird ids should never be used as canonical identity. They are
stored only in observations and latest location metadata.

## Backend Endpoints

Keep the existing selected-message bridge endpoints until the new sync path is
working. Add index endpoints under `/index`.

- `POST /index/runs`: create a run and return `run_id`.
- `POST /index/runs/{run_id}/folders`: record one folder observation.
- `POST /index/runs/{run_id}/messages:batch`: ingest a batch of message
  observations.
- `POST /index/runs/{run_id}/finish`: complete a run and deactivate missing
  locations.
- `POST /index/runs/{run_id}/fail`: mark a run failed with context.
- `GET /index/runs/latest`: return latest run summary.
- `GET /index/runs/{run_id}`: return one run summary.
- `GET /index/messages/{canonical_key}`: return canonical message plus
  locations and recent observations.
- `GET /index/locations/inactive`: list recently inactive locations.
- `GET /index/duplicates`: list canonical keys with multiple active locations.
- `GET /index/folder-errors`: list folder observations with errors.

All debug responses should set `Cache-Control: no-store`.

## Extension Behavior

The browser action should run full mailbox sync for this phase. It should log
clear console breadcrumbs for:

- run start and finish.
- account traversal.
- folder inclusion or skip reason.
- folder page counts.
- batch post success or failure.
- message-level extraction errors.

Failures should be posted to the backend when possible. A failed folder should
not abort the whole run unless the backend run lifecycle itself cannot continue.

Batch size should be fixed and conservative in the first implementation. The
initial target is 50 message observations per request. This is a constant, not a
user-facing setting.

## Testing Plan

### Automated Backend Tests

- Database initialization creates all tables and indexes.
- A run can be opened, receive folder observations, receive message batches, and
  complete.
- Re-ingesting the same canonical message in the same location is idempotent.
- One canonical key can have multiple active locations.
- A later run that misses a previously active location marks it inactive.
- A move-style run creates a new active location and deactivates the old one.
- Missing Message-ID creates a fallback identity and increments fallback counts.
- Failed folder observations appear in folder-error debug output.
- Latest-run and message-debug endpoints return no-store responses.

### Extension Helper Tests

Where practical, pure JavaScript helpers should be separated so they can be
tested outside Thunderbird:

- folder inclusion predicate.
- recursive folder flattening.
- Message-ID normalization.
- body text extraction from nested parts.
- batch construction.

### Manual Thunderbird Tests

Run these against a local SQLite database and inspect debug endpoints after each
step:

1. Full initial sync across all accounts.
2. Restart Thunderbird and run sync again; canonical identities should persist
   while runtime ids may change.
3. Move one message between real folders and confirm old location inactive and
   new location active.
4. Delete one message to Trash and confirm the Trash location appears while the
   source location becomes inactive.
5. Delete one Trash message permanently if Thunderbird exposes the transition
   cleanly; confirm all prior locations become inactive.
6. Archive a Gmail message and confirm the Archive/All Mail-style location is
   represented according to the real folder exposed by Thunderbird.
7. Inspect duplicate endpoint for provider-label duplicates and confirm they are
   locations, not separate canonical messages.
8. Trigger or observe a folder/message fetch failure and confirm it lands in
   folder or observation error output.

## Acceptance Criteria

- A completed sync stores messages from all account-owned non-virtual,
  non-unified, non-tag folders.
- SQLite survives backend restart and still exposes prior runs and locations.
- Duplicate Message-ID groups are represented as one canonical message with
  multiple locations.
- Move/delete/archive/restart tests have clear before/after evidence through
  debug endpoints.
- Folder and message failures are visible without reading ephemeral console
  output.
- No RAG or LLM code is added in this phase.

## Implementation Order

1. Add SQLite schema and store tests.
2. Add run lifecycle and debug endpoints.
3. Add backend batch ingestion tests.
4. Factor Thunderbird extension helpers.
5. Replace browser-action selected-message behavior with full mailbox sync.
6. Run automated verification.
7. Run manual Thunderbird edge-case checks and fix sync bugs found there.
